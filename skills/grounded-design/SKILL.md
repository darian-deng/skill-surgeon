# 需求 → 接地技术方案

把**已决定要做**的需求,拆成一份足够动手实现的方案。本 skill 不绑定产物格式(由调用方指定;无则自维护一份方案大纲)。
若需求还停在「该不该做 / 值不值得」→ 先一两问确认方向,再进入接地。

## 接地优先(每次提问前必做)

提任何问题 / 选项前,先接地:

- **代码库**:grep / read 现有实现、相关模块、已解决过的问题、现有约束。能查清的不问。
- **需求源**:指向 PRD / URL / 文档 → 先完整读取(本地 Read / URL→tavily-extract / 飞书→lark-doc)。
- **外部技术选型 / 依赖接口**(可能在知识截止后已变)→ 查官方文档或 `tvly search`,禁止凭印象推荐。
- **代码库为空(绿地项目)** → 接地重心转到需求源 + 权威资料,「搭基础架构」本身是首批待定决策;此时大量待定点合法地落入「假设」类,这是预期,不是失败。

> **前置 gate(硬性):提第一个问题之前,你的第一条输出必须是一份《现状理解》,这一回合只有 finding、没有问题。** 每条 finding 带可核验来源:`代码: file:line` / `文档: 出处` / `资料: tvly/官方`。给不出来源的不是 finding——删掉或降级为 ⚠ 假设。**没有这份带来源的清单,不得提问。** 唯一例外:连一条可查线索都没有 → 显式声明「无可接地线索,以下按 ⚠ 假设推进」,不许默默跳过。
> (《现状理解》是一次性总览,此处 finding 求全先全列;进入逐节点对齐后,单个 finding 才按「选择性呈现」规则。)

> **铁律:事实型 / 技术型的选项、推荐,若仅凭训练印象,禁止呈现。** 接不了地就继续查;查到 → 塌缩成 finding;谁都查不清 → 降级为 ⚠ 假设。(反例:为「sessionId 怎么填」编了「读 last_session_id」选项,但代码早有多 session 保护——先读代码,这选项当场蒸发成 finding。)**纯产品意图问题不在此列:用开放式提问,不编选项。**

## 三分类:每个待定点归一类,决定怎么呈现

| 类别 | 它是什么 | 处理方式 |
|------|----------|----------|
| **finding** | 代码 / 文档 / 资料能确定的 | 陈述不提问(带来源),**且仅在决策相关 / 可争议 / 带风险时呈现**,其余静默记录 |
| **问开发者** | 只有他知道:意图、取舍、优先级、业务规则、未来计划 | 提问,一次一问 |
| **假设** | 接不了地、且开发者也无法直接拍板的空白 | ⚠ 默认值 + why + **猜错的后果**,不卡住继续走 |

**分不清问谁?按时态裁决**:能陈述「现在是什么」的(它现在怎么做的?有没有 X?用什么库?)一律先查、当 finding;只有「将来应该是什么」才问开发者。半接地的混合项(业务约束 / 限流值 / 权限规则):先查现状固化成 finding,只把意图缺口带着 finding 去问——「现状写死 100 QPS(`rateLimit.ts:20`),沿用还是有新目标?」

## 逐条对齐,不批量

- **先判断需求是否含多个可独立交付的子系统**:是 → 先在顶层切块、定依赖顺序,再逐块走;否 → 直接拆决策树。
- **轻量出口**:改动局限在已知一两处、无设计决策 → 直接接地确认那一两处即可,跳过决策树和 Gate,别把改文案撑成仪式。
- 决策树按依赖排序,**一次走一个分支**。提问附推荐 + 标依据:代码 / 安全 / 最佳实践依据 → 直接给推荐 + 那条依据(档位自明);**仅因省事 → 明说「仅因改动最小,无技术优劣」**;纯意图无依据 → 不给推荐,给「标了代码现状代价」的选项让开发者拍。
  > 「列表怎么展示? 卡片(复用现有 `Card`,和消息页一致)/ 时间线(需新建组件,目前没有)」
- **范围外的想法**(「顺便也做个 X」)→ 记入产物的「暂缓清单」,不丢不做,拉回当前需求。判据:澄清当前需求怎么做 = 继续;能独立成方案的新能力 = 暂缓。
- 每对齐一条**立即增量写入**方案产物,不攒到最后。
- 冒出新待定点 → 回接地再并入;但**不影响 Gate 判定的节点,记录即可、不展开**(防无限发散)。

## 收尾 Gate(质性,不打分)

下列全部「已接地」或「已被开发者拍板」才收尾。**未全绿不许「差不多了」就停**——没接地也没拍板的待定点,要么继续查、要么追问到底:

- **功能边界**:做什么、明确不做什么
- **技术约束**:依赖、兼容性、性能;**若触及数据存储或线上行为,须含数据迁移与回滚 / 灰度方式**
- **关键决策**:每个影响实现的待定点已 finding / 已问 / 已标假设
- **验收标准**:每条可被验证(自动化测试或具体步骤)
